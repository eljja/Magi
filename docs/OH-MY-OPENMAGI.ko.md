# oh-my-openmagi 이름 및 구조 결정

> 2026-09-30 변경: 사용자가 최신 구현을 **oh-my-magi**로 통합해 게시하도록 확정했습니다. 아래 이름 결정은 당시 기록이며, 현재 이름과 설치법은 [0.2.0 통합 배포 기록](OH-MY-MAGI-0.2.0.ko.md)을 따릅니다.

> 구현 안내 (2026-09-25): 이 문서는 개발 전에 확정한 요구사항 원문입니다. 새 구현은 `packages/oh-my-openmagi`에 있으며, 현재 검증 결과와 한계는 [개발·검증 기록](OPENMAGI-RELEASE.ko.md)에 정리했습니다. 아래의 미구현/예정 표현은 설계 확정 당시의 상태입니다.

결정일: 2026-09-24. 상태: 사용자 확정.

## 이름

- 제품명과 향후 npm 패키지명: **`oh-my-openmagi`**
- OpenCode GUI에서 사용자가 선택하는 추가 에이전트: **Magi** (`magi`)
- Council 내부 subagent: **Melchior**, **Balthasar**, **Casper**

향후 재개발과 신규 배포에는 `oh-my-openmagi`를 사용한다. 현재 패키지의 `oh-my-magi` 이름과 설치 명령은 배포명 전환 작업에서 함께 변경한다. 기존 배포와 검증 기록의 이름은 해당 버전을 식별하는 기록으로 보존한다.

## 확정한 동작 구조

1. 기존 OmO 에이전트를 유지하고 GUI 선택지에는 Magi 하나만 추가한다.
2. 사용자는 Magi에 업무를 지시하고, Magi를 통해 진행 상황을 확인하고 개입한다.
3. Magi가 Melchior, Balthasar, Casper를 독립된 council subagent로 호출한다. 세 캐릭터는 GUI의 주 에이전트 선택지에 추가하지 않는다.
4. Magi가 결정한 업무는 기존 OmO 주 에이전트에 위임한다. 업무에 맞는 실행 세션과 담당을 선택하며, 모든 주 에이전트를 매번 거치도록 요구하지 않는다.
5. 실행 담당은 필요한 OmO 전문 subagent를 활용하고, 실행 결과와 검증 증거를 Magi에 반환한다.
6. Magi가 다음 업무와 의회 논의를 조율한다. 목표 수준의 제어와 위임된 작업 내부의 실행 제어를 구분한다.

위 내용은 재개발의 목표 구조다. 기존 코드에서의 세션별 제어 범위와 실행 담당 선택은 구현·검증 대상으로 남아 있다.

## 사용자 확정 운영 정책

확정일: 2026-09-25. 사용자가 아래 세 가지 추천안에 모두 동의했다. 재개발 구현과 검증의 기준으로 적용한다.

### 자율 확장 범위

기존 기능 개선뿐 아니라 **원래 목표에 직접 도움이 되는 새 기능 추가까지 허용**한다. Magi와 council은 관련성·기대 효과·검증 방법을 근거로 업무를 선정한다. 목표 자체의 변경은 사용자에게 제안하며, 답변을 기다리는 동안 원래 목표와 승인된 범위에서 가능한 업무를 계속한다.

### 의회 의결 기준

세 인격의 유효한 최종 표를 모두 받은 뒤 **2명 이상 찬성하면 실행을 승인**한다. 누락·오류 응답을 표로 간주하거나 두 표만으로 조기 승인하지 않는다. 일반적인 한 명의 반대는 단독 거부권이 아니다.

구체적인 데이터 손실·보안 위험이 제기된 안건은 보완 후 재심의한다. 해당 위험의 근거와 필요한 보완을 기록하고 해결 여부를 검증한다. 이 경우에도 전체 목표를 중지하지 않고 보완·조사 또는 다른 허용 업무를 진행한다. 승인과 재심의 결과를 실제 적용한 규칙과 함께 이력에 남긴다.

### 외부 행동과 비용 권한

목표와 지정한 프로젝트 범위 안에서 **로컬 수정·테스트를 자동 수행**한다. 게시·배포·결제 같은 외부 행동은 **사용자가 명시적으로 부여한 권한에 따라 수행**한다. 이미 부여된 권한은 해당 범위에서 유지하며 같은 권한을 매번 다시 묻지 않는다.

모델과 대체 모델은 **사용자가 지정한 범위만 사용**한다. 장애 복구를 이유로 승인되지 않은 모델·제공자·요금제로 임의 전환하거나 결제하지 않는다. 필요한 의존성이 없으면 목표 운영 의사를 유지하며 회복 또는 사용자 조치를 기다린다.

위 정책은 사용자가 나중에 설정으로 변경할 수 있게 한다. 기술 스택, 모듈 분리, 저장 방식, 재시도·복구 구현과 테스트 구성 등 구현 세부 사항은 개발 과정에서 결정한다.

## 지속 운영 요구사항

사용자의 명시적 중지만 목표를 중지한다. 개별 업무 완료 뒤에는 권한 안에서 다음 개선을 찾고, 네트워크·모델·API 오류는 대기와 자동 복구로 처리한다. 목표 운영 의사와 현재 실행·대기 단계를 분리하며, GUI와 독립된 프로세스 감독 및 지속 저장을 설계한다. 상세 요구사항과 검증 기준은 [지속 운영 설계](CONTINUOUS-RUNTIME.ko.md)에 기록한다. 구현과 실제 모델 장시간 검증은 아직 완료되지 않았다.

## Council 현재 투표와 누적 이력

확정일: 2026-09-25. 사용자는 현재 투표와 같은 형식의 누적 이력을 요구하며, 호환성과 구현 부담을 줄이기 위해 추가 UI를 만들지 않기로 했다. 아래 내용은 구현 전 요구사항이다.

### 공통 표시 형식

현재 투표와 과거 투표 모두 동일한 간결한 블록으로 표시한다. 회의 번호·라운드·시각을 짧은 머리말로 두고 다음 네 줄을 제공한다.

1. 투표 주제 한 줄.
2. Melchior의 의견 요약 한 줄과 찬성·반대 표시.
3. Balthasar의 의견 요약 한 줄과 찬성·반대 표시.
4. Casper의 의견 요약 한 줄과 찬성·반대 표시.

일반 Markdown/텍스트에서 `🟢 찬성`·`🔴 반대`를 사용한다. 색을 표시하지 못하는 환경에서도 상태 텍스트로 의미를 전달한다. 투표 전·응답 대기·재시도는 `대기`로 구분하며 반대표로 계산하지 않는다. 기존 `revise`를 유지하는 경우 `🟡 보완 요청`으로 표시하며 찬반과 구분한다. 전체 승인 여부는 각자의 찬반과 별개로 실제 적용한 의결 규칙에 따른 결과를 기록한다.

의견 요약은 해당 인격이 실제로 제출한 근거에서 가져온다. 구조화 응답에 짧은 요약을 포함시키고 전체 의견도 보존한다. 표시만을 위해 추가 모델 호출을 발생시키지 않는다. 문장 자체는 한 줄로 기록하되 좁은 기본 문서 뷰어의 자동 줄바꿈은 허용한다.

### 문서와 기본 화면 사용

- `.magi/VOTES-LATEST.md`: 진행 중인 회의의 주제와 세 인격의 최신 유효한 의견·투표를 갱신한다. 실행 단계에는 마지막 확정 투표와 실행 상태를 유지한다.
- `.magi/VOTES.md`: 확정된 회의/라운드를 같은 형식으로 시간순 누적한다. 새 기록은 끝에 추가하며 승인·반대·보완 요청 결과를 모두 남긴다.
- `.magi/COUNCIL.md`: 전체 의견, 토론, 판단 근거와 실행 결과를 담는 상세 회의록으로 유지한다.
- GUI에서는 기본 우측 문서창으로 위 문서를 열어 확인한다. CLI/TUI에서는 동일한 문서를 기본 파일 조회·터미널 출력으로 확인한다. 파일 변경 추적이 필요하면 기존 터미널 기능을 사용한다.
- 전용 GUI 패널, 새 TUI 위젯, 웹 대시보드, 브라우저 확장, 별도 문서 뷰어를 새로 개발하지 않는다. 해당 UI의 설치를 동작 요건으로 삼지 않는다. 기존 제품의 UI 코드는 이번 요구사항 기록만으로 삭제하지 않는다.
- 기본 문서창의 파일 변경 감지와 자동 갱신은 대상 OpenCode 버전에서 확인한다. 지원되지 않는 경우 기본 다시 열기/새로고침을 안내하며 자동 갱신을 약속하지 않는다. 임의 HTML·글자색·스크립트 실행에 의존하지 않는다.

### 누적과 복구

- 현재 상태와 이력은 동일한 저장된 투표 데이터를 사용한다. 목표·회의·라운드 ID로 구분하여 이전 회의의 표가 새 안건에 붙지 않게 한다.
- 각 인격의 유효한 응답이 들어오는 대로 최신 문서를 갱신한다. 초기 의견을 최종 표로 표시하지 않는다. 부분 응답과 재시도 경과는 상세 기록에 보존한다.
- 확정된 회의/라운드는 식별자로 중복 기록을 방지한다. 프로세스 재시작과 재시도 때문에 같은 투표 이력을 여러 번 추가하지 않는다.
- 제안 수정과 재투표는 새 라운드로 남긴다. 이전 반대표와 근거를 나중의 찬성 결과로 덮어쓰지 않는다.
- 재접속 때 저장된 최신 상태를 복구한다. 최신 문서에는 마지막 갱신 시각을 포함하고 감지한 오류와 재시도 상태를 기록한다. 호스트가 꺼져 갱신할 수 없는 문서를 실시간 연결 상태라고 보장하지 않는다.
- 기록이 커지면 과거 이력을 날짜별 문서로 나누고 이력 문서에서 연결한다. 과거 투표는 보존하며 루프 횟수에 제한을 두지 않는다.
- 문서 닫기나 표시 문제는 지속 실행을 중지하지 않는다. 문서 생성 오류는 원본 투표 기록을 유지한 채 복구·재생성하고 상태에 반영한다.

## 정기 진행 보고

확정일: 2026-09-25. 기본 보고 간격은 **1시간**으로 설계한다. 사용자가 운영을 신뢰하게 되면 2시간·4시간 등으로 늘리거나 필요에 따라 줄일 수 있다. Magi가 스스로 잘하고 있다고 판단해 보고 간격을 임의로 늘리지 않는다. 현재 기존 패키지의 기본값은 4시간이며, 아래 정책과 명령은 신규 구현 대상이다.

### 보고 시점과 내용

- 목표를 시작한 시각부터 지정한 간격마다 보고한다. 작업·회의·검증이 진행 중이어도 완료를 기다리지 않는다.
- 보고 주기는 운영 의사가 `running`인 동안의 경과 시간을 기준으로 한다. API 오류, 인증 문제, 사용량 제한, 재시도와 재평가 대기도 포함한다. 유효한 진전이 없으면 그 사실과 이유를 보고한다.
- 보고는 짧은 요약을 기본으로 하고 현재 업무와 실행 담당, 지난 보고 이후 확인된 성과·검증 결과, 최근 의회 결정, 장애·대기 이유와 다음 재시도, 다음 업무 또는 검토 후보, 다음 정기 보고 시각을 담는다. 근거 없는 진행률이나 예상 완료 시각을 만들지 않는다.
- Magi와 대화하던 원래 세션에 자동 보고로 전달하고 `.magi/LATEST-REPORT.md` 및 `.magi/reports/`에도 보존한다. GUI와 CLI의 기본 대화·문서 기능을 사용하며 추가 UI는 만들지 않는다.
- 명시적 사용자 중지 이후 정기 보고를 멈춘다. 재개 시 새 보고 시각을 계산하고 알린다. 현재 상태를 묻는 요청은 중지 상태에서도 응답할 수 있다.
- 호스트가 꺼져 있던 동안 실제 보고는 보낼 수 없다. 재시작 시 보고 기한을 넘겼다면 공백과 복구 상태를 한 번에 요약하고 다음 시각을 잡는다. 누락된 시간 수만큼 과거 보고를 쏟아내지 않는다.

### 사용자 조절

다음은 구현할 명령 형식이다. 아직 현재 배포판에서 지원하는 명령으로 안내하지 않는다.

| 명령 예시 | 동작 |
| --- | --- |
| `/magi report interval 1h` | 보고 간격을 1시간으로 설정 |
| `/magi report interval 30m` | 보고 간격을 30분으로 설정 |
| `/magi report interval 4h` | 보고 간격을 4시간으로 설정 |
| `/magi report now` | 현재 상황을 즉시 보고 |
| `/magi report status` | 현재 간격과 다음 보고 시각 조회 |

일반 대화의 “앞으로 한 시간마다 보고해”, “보고 간격을 30분으로 줄여”, “이제 네 시간마다 보고해도 돼”, “지금 진행 상황 알려줘”도 동일한 제어 동작으로 처리한다. 보고 간격을 바꾸는 사용자 지시는 작업 목표 변경이나 council 안건으로 넘기지 않고 즉시 적용한다.

설정은 현재 목표에 저장하고 재시작 후에도 유지한다. 변경 시 적용된 간격과 다음 보고 시각을 사용자에게 알려준다. 새 간격은 변경 시점부터 계산한다. 단위나 의도가 불명확하면 기존 설정을 유지하고 필요한 부분만 확인한다. 0·음수·잘못된 단위는 간격으로 적용하지 않는다. 명령 경로는 LLM 호출 없이 처리하고, 자연어 변경도 실제 저장에 성공한 뒤에만 적용됐다고 말한다.

### 작업과 독립된 전달 및 복구

- 보고 스케줄러는 실행·의회·검증 요청과 독립적으로 동작한다. 오래 걸리는 모델 요청 때문에 보고가 지연되지 않게 한다. 보고를 위해 작업을 중단하거나 별도 회의를 열지 않는다.
- 기본 보고는 저장된 실제 상태와 증거로 구성하여 추가 LLM 호출에 의존하지 않는다. LLM 제공자가 고장 나도 상태를 보고할 수 있어야 한다.
