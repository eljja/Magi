## 운영 계약

사용자가 부여한 목표와 권한 안에서 개발·연구·개선을 계속한다. 초기 요청이나 개별 작업의 완료는 다음 개선 주기를 시작하는 계기다. 사용자의 명시적 중지 요청만 목표의 운영 의사를 중지 상태로 바꿀 수 있다.

- Magi와 council은 다음 업무를 결정하고 OmO 실행 담당에게 위임한다.
- 개별 업무는 완료할 수 있다. 전체 지속 목표에는 자동 완료 전이를 두지 않는다.
- 모델의 최종 응답, 도구 호출 종료, 세션 idle, 시간 초과, 네트워크·제공자 오류, 잘못된 결정 응답은 사용자 중지 요청이 아니다.
- 일시적 오류와 재시도 횟수 누적만으로 목표를 포기하거나 자동 종료하지 않는다.
- 재부팅·프로세스 재시작 뒤에도 실행 의사와 진행 기록을 복구한다. 명시적으로 중지된 목표는 재시작으로 되살리지 않는다.

## 목표의 운영 의사와 현재 상태

지속 저장하는 운영 의사(`desiredState`)는 `running`과 `stopped`로 구분한다. 현재 수행 단계(`phase`)와 독립적으로 관리한다.

| 상황 | 현재 단계 | 다음 동작 |
| --- | --- | --- |
| 업무의 결과와 검증 증거가 돌아옴 | `planning` | 남은 문제와 새 개선 후보를 평가하고 다음 업무 승인 |
| 승인한 업무 수행 중 | `executing` | 실행 담당과 하위 작업의 진행 감시 |
| timeout, 연결 끊김, 429, 일시적 서버 오류 | `retry_wait` | 재시도 시각을 저장하고 대기 후 상태 재조회·복구 |
| 인증 만료, 잔액 부족, 필요한 권한·정보 부재 | `dependency_wait` | 필요한 조치를 알리고 의존성 회복을 확인; 가능한 독립 업무는 계속 |
| 프로세스 재시작, 실행 결과 불명확 | `recovering` | 저장 상태와 실제 산출물·실행 세션을 대조하고 이어가기 |
| 당장 근거 있는 개선 후보가 없음 | `scheduled_review` | 목표를 유지하고 정해진 시각이나 새 증거에 따라 재평가 |
| 사용자 명시적 중지 | `stopped` | 운영 의사를 저장하고 진행 중 시도를 취소; 명시적 재개까지 유지 |

대기 중에는 실행 중인 것처럼 표시하지 않는다. 대기 이유, 마지막 유효한 진전, 다음 확인 시각을 보여준다. 목표의 운영 의사는 유지한다.

## 지속성을 담당하는 런타임

1. **외부 프로세스 감독:** GUI와 분리한 백그라운드 OpenCode 서버와 프로세스 감독자가 필요하다. 플러그인 내부 타이머만으로 자기 프로세스의 종료를 복구할 수 없다. OS 시작 시 복구는 해당 실행 환경의 서비스 등록으로 구성한다.
2. **단일 목표 제어자:** 목표별 활성 제어자는 하나만 둔다. 제어권을 넘길 때 이전 실행의 늦은 응답이 현재 상태를 바꾸지 못하도록 실행 세대와 소유권을 확인한다.
3. **지속 저장:** 목표, 권한 범위, 사용자 개입, 회의별 유효한 표, 승인 업무 ID, 실행 시도, 검증 증거, 재시도 시각, 중지 기록을 저장한다. 부분 회의와 부분 실행을 처음부터 반복하지 않는다.
4. **두 단계 감시:** 각 모델·도구 요청에는 유한한 제한 시간을 둔다. 별도의 감독자가 제어 루프의 heartbeat와 유효한 진전을 감시하여 응답을 기다리던 루프 자체가 멈추는 경우도 복구한다. heartbeat가 있다는 사실만으로 업무가 진전됐다고 판정하지 않는다.
5. **오류별 재시도:** 일시적 오류는 지수 백오프, 무작위 분산, 최대 대기 간격을 적용하고 제공자의 Retry-After를 존중한다. 인증·결제·권한 문제는 빠른 반복 호출 대신 변경 감지와 낮은 빈도의 확인을 사용한다. 대기 간격 상한은 목표 재시도 횟수 상한이 아니다. 계층별 재시도가 겹쳐 호출량을 증폭하지 않도록 책임을 정한다.
6. **중복 실행 방지:** timeout은 원격 작업 실패의 증거가 아니다. 기존 작업과 산출물을 먼저 확인하고 승인 업무 ID로 이어간다. 외부 부작용은 가능한 경우 멱등 키를 쓰고, 결과가 불명확하면 재실행 전에 대조한다.
7. **사용자 중지의 출처:** 사용자 제어 경로에서 확인한 명시적 중지만 중지 전이를 허용한다. LLM의 stop 도구 호출이나 MessageAbortedError만으로 사용자 의사를 추정하지 않는다. 모델이 읽는 작업 파일과 모델 출력만으로 중지 기록을 위조할 수 없도록 경계를 설계한다. 사용자 중지는 재시도·늦은 결과보다 우선한다.

OpenCode는 GUI 없이 실행하는 `opencode serve`와 세션 조회·메시지·비동기 실행 API를 제공한다. 이는 런타임 구성의 기반이며, 프로세스 자동 재시작과 위의 운영 계약이 이미 제공된다는 뜻은 아니다. [공식 서버 문서](https://opencode.ai/docs/server/)

전원과 실행 호스트가 꺼져 있거나 모든 모델 제공자가 사용 불가능한 동안에는 실제 모델 작업을 할 수 없다. 요구하는 보장은 실행 의사를 보존하고, 호스트와 필요한 의존성이 회복되면 사용자 재개 명령 없이 작업을 복구하는 것이다. 사용자가 중지한 경우는 제외한다.

## 다음 개선 업무 선택

각 실행 결과를 근거로 남은 결함, 회귀, 정확성, 재현성, 성능, 사용자 경험, 유지보수성의 개선 후보를 갱신한다. council이 원래 목표와의 관련성, 기대 효과, 비용, 위험, 검증 방법을 따져 다음 업무를 고른다.

2026-09-25 사용자 확정 정책에 따라 원래 목표에 직접 도움이 되는 새 기능도 자율 개선 범위에 포함한다. 세 명의 유효한 최종 표를 모두 확보한 뒤 2명 이상 찬성으로 승인하며, 구체적인 데이터 손실·보안 위험은 보완 후 재심의한다. 로컬 수정·테스트는 자동 수행하고, 게시·배포·결제와 모델 선택은 사용자에게 부여받은 권한 범위를 따른다. 자세한 기준은 [사용자 확정 운영 정책](OH-MY-OPENMAGI.ko.md#사용자-확정-운영-정책)에 따른다.

권한 안에서 기능 확장과 개선을 추진한다. 권한 밖의 행동은 후보와 필요한 조치를 기록하고, 독립적으로 진행 가능한 업무를 선택한다. 변경 횟수나 도구 호출량을 성과로 취급하지 않으며, 할 일을 만들기 위한 반복 재작성과 같은 조사의 무한 반복을 피한다. 현재 증거로 유용한 개선이 없으면 목표를 완료 처리하지 않고 재평가를 예약한다.

## 작업과 독립된 정기 보고

2026-09-25 추가 요구: 기본 1시간마다 원래 Magi 대화와 보고 문서에 현재 상태를 전달한다. 사용자는 명령 또는 일반 대화로 간격을 변경하며, 변경은 즉시 저장하고 다음 보고 시각을 알려준다. Magi는 보고 간격을 임의로 늘리지 않는다.

모델 응답·업무 완료를 기다리지 않는 독립 스케줄러가 필요하다. 운영 중인 동안 오류와 재시도 대기도 시간에 포함한다. 목표가 중지되면 정기 보고도 중지한다. LLM 장애 시에도 기록된 사실로 보고하고, 호스트 종료로 놓친 보고는 재시작 후 한 번으로 요약한다. 보고 전달 실패가 다음 보고 생성이나 작업 복구를 가로막지 않게 한다. 상세 명령·내용·전달 정책은 [정기 진행 보고 설계](OH-MY-OPENMAGI.ko.md#정기-진행-보고)를 따른다.

## 현재 저장소에서 확인한 차이

- `packages/oh-my-magi/src/continuation.ts`에는 지속 모드와 오류 백오프가 있다. 레거시 `complete` 모드는 전체 로드맵 완료 시 `loopActive: false`로 전이한다.
- `packages/oh-my-magi/src/server.ts`는 알려진 복구 취소를 제외한 일부 `MessageAbortedError`와 소유 세션 삭제를 전체 루프 중지로 처리한다. 명시적 사용자 중지와 실행 시도 중단을 구분해야 한다.
- 현재 `magi_stop`은 호출 세션의 소유권을 검사하지만, 해당 호출이 사용자의 명시적 중지 요청에 대응하는지 별도 증거를 검사하지 않는다.
- 현재 주기 타이머와 watchdog은 OpenCode 플러그인 프로세스 안에서 동작한다. 프로세스 종료·재부팅 복구에는 외부 감독과 시작 구성이 필요하다.
- 다른 환경에서 보고된 실제 중지 원인은 그 환경의 버전·설정·이벤트 기록으로 별도 확인해야 한다.

## 구현 후 통과해야 할 검증

1. 초기 업무와 원본 검증을 마친 뒤 사용자 추가 지시 없이 근거 있는 다음 개선 업무를 시작한다.
2. 스트림 단절, timeout, 429, 5xx를 발생시킨 뒤 의존성이 회복되면 같은 목표를 자동 재개한다.
3. 인증이나 사용량 제한이 유지되는 동안 대기 상태와 사유를 표시하고, 해결 뒤 자동 재개한다.
4. 회의·위임·실행·검증 각 단계에서 프로세스를 강제 종료하고 재시작해 기록을 복구한다. 완료된 외부 효과를 중복 수행하지 않는다.
5. 이벤트 누락과 영구 대기 요청이 있어도 감독자가 정체를 감지하고 복구한다. 중복 제어자는 생기지 않는다.
6. 모델의 완료 선언과 잘못된 stop 호출만으로 전체 목표가 중지되지 않는다. 명시적 사용자 중지는 즉시 반영하고 재부팅 후에도 유지한다.
7. 잘못된 표와 중복 결정 호출을 승인으로 처리하지 않는다. 유효한 부분 결과를 보존하고 해당 결정만 복구한다.
8. 실제 모델 장시간 운전에서 유효한 개선 성과, 복구 시간, 비용, 중복 실행 여부를 측정한다. 짧은 회귀 검사를 무한 운전 보증으로 표현하지 않는다.
9. 실행·의회·검증이 보고 간격보다 오래 걸리거나 LLM이 실패 중이어도 예정 시각에 사실 기반 상태 보고를 생성한다. 보고가 실행을 취소하거나 새 작업을 시작하지 않는다.
10. 명령과 일반 대화로 간격을 줄이거나 늘렸을 때 같은 설정과 다음 보고 시각을 적용하고 재시작 후에도 유지한다. 즉시 보고가 정기 보고를 무기한 연기하지 않는다.
11. 보고 전달 단절 중에도 다음 정기 보고를 생성하고 작업을 계속한다. 재연결 시 중복·과거 알림 폭주 없이 최신 상황을 전달한다. 사용자가 중지한 뒤에는 정기 보고를 재개하지 않는다.
