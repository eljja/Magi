# 실제 PC 가동 전 점검 — 2026-09-09

OMM은 공식 `oh-my-opencode@4.19.4`를 직접 로드하고 그 위에서 하나의 목표와 회의·검증·보고·지속 실행을 관리한다. Sisyphus와 전문 에이전트는 실제 OmO 구현이다.

## 이번에 수정한 여섯 영역

| 영역            | 구현과 확인 방법                                                                                                                                                                                                                                                                                   |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 공개 설치       | GitHub 공개 여부와 npm 배포는 별개다. 공개 배포 설정, 라이선스 고지, 서버/TUI 산출물, 네이티브 설치 검증 및 배포 워크플로를 준비했다. 실제 게시 결과는 [출시 감사](RELEASE-AUDIT.md)에 기록한다.                                                                                                   |
| 기존 OmO와 공존 | 인식 가능한 전역·상위 디렉터리·프로젝트·명시적 설정의 OmO 서버/TUI 등록을 OMM으로 전환한다. 원본과 경로를 `.magi/backups/`에 보관하고 모델 설정·주석·다른 플러그인은 유지한다. 시작 중 전환됐다면 한 번 재시작해야 한다. 이전 설정으로 이미 만들어진 OmO 위에 두 번째 실행 시스템을 만들지 않는다. |
| 지속적인 회의   | `maxCycles`와 `maxDebateRounds`는 모두 0으로 정규화한다. 거절된 회의는 같은 회의 번호와 다음 라운드로 이어지며 반론을 반영해 제안을 수정한다. 한 스케줄러 턴에 한 라운드를 저장하므로 보고·중지가 가능하다. 최근 라운드는 모델 문맥에, 전체 기록은 파일에 남는다.                                  |
| 회의록과 기억   | 기존 `COUNCIL.md` 장치를 유지했다. 원문 지침은 `USER-GUIDANCE.md`, 승인된 기억 요약은 `MEMORY.md`에 보존한다. 다음 회의와 세션 압축이 이 파일을 실제로 읽는다. 큰 파일은 발췌와 원문 경로를 제공하고 시간순 원문이 요약보다 우선하도록 지시한다.                                                   |
| 장기 실행 복구  | 진전 없는 세션을 감지해 중단 후 승인 작업을 복구한다. OS 소켓 기반 소유권은 프로세스 종료 시 해제되며 잘못된 잠금 JSON이 실행을 막지 않는다. 검증 시간 초과는 자식 프로세스와 출력도 정리한다. 검증 설정 누락은 회의 전에 알리고 장애는 대기 간격을 늘려 재시도한다.                               |
| 현재·향후 버전  | SDK/plugin을 1.18.30으로 맞추고 OmO 4.19.4를 고정했다. `compatibility.json`, 레지스트리 비교 스크립트, 3개 OS × 최소/최신 OpenCode CI를 추가했다. 새 버전 지원은 통합 검증 후 기준을 갱신한다.                                                                                                     |

## Windows에서 추가로 발견한 문제

OpenCode 1.18.30 실행 중 Bun의 ReadOnly 디렉터리 mkdir 오류를 재현했다. OMM은 알려진 런타임 디렉터리 속성을 복구하며 파일 내용과 ACL은 변경하지 않는다. 플러그인 로드 전에 OpenCode가 `EEXIST`로 종료되면 다음 명령으로 복구하고 재시작한다.

```sh
bunx oh-my-magi doctor --repair-windows --project <프로젝트 경로>
```

근거: [Bun #34413](https://github.com/oven-sh/bun/issues/34413). 상위 OmO 중지 훅이 실패해도 OMM의 영속 중지 상태를 먼저 저장하도록 수정했다.

## 첫 가동

1. 프로젝트에서 `opencode plugin oh-my-magi`를 실행한다. 기존 OmO 전환 안내가 나오면 OpenCode를 한 번 재시작한다.
2. OpenCode의 모델 연결과 `.omo/omo.jsonc`의 OmO 모델 설정을 확인한다.
3. `.magi/config.jsonc`에 실제 프로젝트 검증 명령을 지정한다. 연구라면 실험 산출물·데이터 무결성·재현성을 확인하는 명령을 사용한다.
4. `/magi start <하나의 목표>`로 시작한다. 이후 우선순위나 질문은 같은 세션에서 평소처럼 대화한다.
5. `.magi/index.html`, `STATUS.md`, `COUNCIL.md`를 확인한다. `/magi stop`은 중지하고 `/magi resume`은 같은 목표를 재개한다.

## 검증 범위와 남은 운영 조건

전체 단위·회귀 검증은 **81개 테스트, 327개 assertion, 실패 0개**이며 타입 검사와 빌드가 통과했다. 실제 통합 실행 및 배포 결과는 [출시 감사](RELEASE-AUDIT.md)를 따른다.

결정론적 모델 테스트는 실행 연결과 상태 전이를 확인한다. 실제 내부 LLM의 장시간 판단 품질, 모든 에이전트·모델 조합, 모든 GUI 화면을 보증하지는 않는다. 기존 OmO 기능은 로드되지만 모델·권한·설정 제약은 그대로 적용된다.

OpenCode와 모델 서버가 살아 있어야 실행된다. 절전·전원 종료 이후 OS 자동 시작은 설치하지 않는다. 승인 대기나 인증 문제에는 사용자 개입이 필요할 수 있다. 회의록과 세션은 누적되므로 장기 운영 시 디스크 감시와 외부 아카이브가 필요하다. 사용자 정의 플러그인 래퍼와 인라인 환경 설정은 자동 전환 범위 밖이다.

이는 목표나 회의 반복 횟수를 제한한다는 뜻이 아니다. 실제 검증 증거와 남은 환경 조건을 구분한 것이다.
