# oh-my-openmagi 0.1.0 개발·검증 기록

작성일: 2026-09-25. 새 패키지는 `packages/oh-my-openmagi`에 독립 구현했습니다. 기존 `packages/oh-my-magi` 코드는 변경하지 않았습니다. npm 게시와 OS 서비스 등록은 이번 개발 작업에서 수행하지 않았습니다.

추가 심층 검토의 수정 항목, 잔여 의존성 경고와 최종 시험은 [심층 재검증 기록](OPENMAGI-DEEP-AUDIT.ko.md)에 정리했습니다.

## 구현 범위

| 영역        | 구현                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| 진입점      | Magi primary 1개, 숨겨진 council subagent 3개                                                        |
| 의회        | 별도 세션의 초기 의견 → 상호 열람 → 세 유효 최종 표 → 2표 이상 찬성                                  |
| 위험 제기   | 구체적인 보안·데이터 손실 근거가 있으면 보완 후 새 라운드                                            |
| 실행        | 원본 OmO 4.19.4의 Sisyphus·Hephaestus·Prometheus·Atlas에 세션으로 위임                               |
| 지속 운영   | SQLite에 운영 의사·단계·업무·투표·보고·재시도 시각 저장                                              |
| 복구        | 저장 후 제출, 고정 메시지 ID 확인, 지수 대기와 jitter, Retry-After, 명시한 모델만 fallback           |
| 사용자 제어 | 직접 입력한 중지·재개·보고 명령, 한국어 보고 간격 변경, 중지 후 자동 재개 금지                       |
| 검증        | 실행 증거와 별도 명령 결과 저장; 미설정·실패를 성공으로 포장하지 않음                                |
| 보고        | 기본 1시간, 실행/의회/오류 대기 중에도 독립 생성, durable outbox, 재연결 시 묶음 전달                |
| 표시        | Markdown 현재 투표·누적 이력·상세 회의록·보고; 신규 GUI/TUI/웹 UI 없음                               |
| 프로세스    | 독립 supervisor, 자기 소유 프로세스 감시/재시작, loopback 인증, OS 시작 등록용 템플릿                |
| 설치/배포   | 기존 등록 백업·이전, 표준 plugin/CLI exports, 배포 tarball 설치 검사, 호환성 CI와 수동 게시 workflow |

기존 회의록·투표·보고 파일은 첫 표시 생성 전에 `.magi/backups/documents-<generation>/`에 보존합니다. 일반 세션 목록의 100개 제한에 의존하지 않고 부모·하위 세션과 제출 메시지를 직접 조회하며, 삭제된 작업 세션도 운영 중지로 처리하지 않습니다.

제어 데이터는 프로젝트 밖의 사용자별 경로에 저장합니다. 문서 파일은 저장 데이터의 표시본입니다. 회의 ID를 기준으로 이력을 중복 없이 재생성하고, 이전 표를 다음 회의의 표로 표시하지 않도록 검증했습니다.

## 수행한 검증

Windows 환경, Bun 1.3.13에서 실행했습니다.

| 검사                                                          | 결과                           |
| ------------------------------------------------------------- | ------------------------------ |
| `bun install --frozen-lockfile --ignore-scripts`              | 통과, 잠금 파일 추가 변경 없음 |
| 패키지 `bun typecheck`                                        | 통과                           |
| 패키지 `bun test`                                             | **44개 통과, 160개 assertion** |
| Prettier 검사                                                 | 통과                           |
| 빌드·tarball 생성·격리 설치·CLI·plugin export 검사            | 통과                           |
| OpenCode 1.18.31 + 최종 배포 파일 + 실제 OmO + 로컬 모델 서버 | 통과                           |
| OpenCode 1.18.29 + 같은 최종 배포 파일 + 실제 백그라운드 위임 | 통과                           |

자동 테스트는 잘못된/누락된 표의 비승인, 일부 표 보존, 근거 있는 위험과 일반 반대의 구별, 명시한 대체 모델, 응답 유실 후 중복 제출 방지, 비동기 처리 도중 중지, 컨트롤러 상호 배제, 실행 중단의 증거 보존, 보고 전달 장애와 재연결, 중지의 지속성, 설치 백업, 별도 감독 프로세스의 실제 자식 재시작을 다룹니다.

네이티브 통합 시험은 **실제 OpenCode 실행 파일과 수정하지 않은 OmO 패키지**를 사용합니다. 모델 서버만 결정적인 로컬 fixture로 교체했습니다. 다음 경로를 확인했습니다.

1. 네이티브 설치 후 Magi primary, 숨겨진 세 council agent, 기존 OmO agent가 등록됨.
2. 일반 Magi 대화로 목표를 시작하고 실제 세 개의 초기 의견과 세 개의 최종 표를 받음.
3. Sisyphus의 실제 `task` → `explore` → `read`가 fixture 파일의 내용을 회수함.
4. 사용자 지정 검증 명령을 실행하고 다음 회의로 계속 진행함.
5. 정기 보고를 원래 대화에 전달함.
6. 한국어로 보고 간격을 변경함.
7. OpenCode 프로세스 트리를 강제 종료·재시작해 같은 목표를 계속함.
8. `/magi stop` 뒤 다시 재시작해도 중지 상태가 유지됨.

최소 버전 시험에서는 `run_in_background=true`와 실제 `background_output`을 통한 결과 회수도 확인했습니다. Windows 프로세스 정리는 생성한 프로세스의 부모·생성 시각을 확인하고 해당 트리만 대상으로 합니다.

## 배포 파일

파일: `packages/oh-my-openmagi/artifacts/oh-my-openmagi-0.1.0.tgz`

SHA-256: `46763eff60c3e5ed6f0958640e35210c54dcfeab076f84338d9b43ea9294aab6`

`artifacts/release.json`에는 파일 경로·해시·격리 설치 경로와 최종 검증 요약이 들어 있습니다. 두 버전의 상세 결과는 `artifacts/validation/opencode-1.18.29.json`, `opencode-1.18.31.json`에 보존했습니다. 최종 시험에서는 테스트 스크립트의 별도 Windows 복구 보정 없이 패키지 자체의 처리를 사용했습니다. 생성된 배포 파일은 Git에서 제외하며 `bun run pack:check`로 다시 만들 수 있습니다. 게시 workflow는 검증한 tarball을 그대로 게시합니다.

CI에는 Windows·Linux·macOS × OpenCode 1.18.29·1.18.31 조합을 구성했습니다. 게시 workflow는 이 호환성 작업을 의존성으로 실행하고, 자체 tarball 검사와 통합 검증을 다시 거친 뒤 npm trusted publishing을 사용합니다. 첫 게시 전에 해당 npm 계정의 이름 소유권/게시 권한과 trusted publisher, GitHub `npm` environment를 설정해야 합니다. 이 설정이나 workflow 실행을 완료했다고 가정하지 않습니다.

## 검증의 한계

- 위 네이티브 시험은 결정적 모델 응답을 사용했습니다. 유료·실제 모델을 이용한 수일간 연속 운전과 결과물의 장기 품질은 별도 운영 검증 대상입니다.
- Linux/macOS CI와 실제 OS 재부팅·서비스 등록 시험은 이번 Windows 로컬 실행 결과에 포함하지 않습니다.
- GUI의 파일 자동 갱신은 제품/버전에 따라 다릅니다. 새 전용 패널을 만들지 않았고 자동 갱신을 보장하지 않습니다.
- 호스트 전원, 디스크, 자격증명 등 실행에 필요한 조건 자체가 없는 동안 작업할 수는 없습니다. 운영 의사와 복구 상태를 보존하고 가능한 때 재개하는 구조입니다.
- 고정 ID와 상태 확인은 중복 제출을 줄입니다. 임의의 외부 API·셸 부작용 전체에 대한 exactly-once 보장은 아니므로, 중단된 실행의 증거를 다음 의회에 넘겨 실제 상태를 먼저 확인하게 합니다.
- 도구 수준 제어 보호는 실수 방지이며 OS 격리를 대체하지 않습니다. 기존 OpenCode 권한을 유지합니다.

이전 무료 모델·GUI·레거시 운전 감사는 기존 `oh-my-magi`에 대한 기록입니다. 이번 패키지의 시험 결과와 혼합하지 않습니다.
